Claims Backend v2

Postgres holds every fact and every deadline. Temporal, the platform other teams already run, runs short workflows that act on them: each is started by a deadline coming due or by something that happened, and finishes within minutes to days. Payments run as a daily batch that doesn't depend on Temporal.

Components and how they talk

How a deadline fires

Every deadline, from status letters to hold reviews, goes through the same six steps.

How an event starts a workflow

Anything a person does, like uploading proof, recording a decision or closing a claim, goes through the outbox.

No workflow waits for weeks. Anything that needs to happen later is a deadline. That's why each run can stay pinned to the code build it started on, and why the long versioning section in v1 is no longer needed.

Decisions in v2

  • Temporal staysIt's an existing platform that other teams run. We use our own namespace and task queues.
  • Deadlines are dataEvery deadline is a row in Postgres, not a Temporal timer.
  • No long-running workflowsWorkflows last minutes to days. Continue-as-new and long-lived patches are not needed.
  • Outbox for every eventThe API never starts a workflow directly. It writes an outbox row with the change.
  • Payments don't depend on TemporalThe payment run has its own scheduler and can be started by hand, so an outage on the shared platform can't stop payments.
  • Java 21 and Spring BootThis is assumed, as in v1. With .NET the shape is the same.
