With and Without Temporal

One job, built two ways. On day 42 the examiner approves Sam's claim, and three things must follow: send the approval letter, start the premium waiver in policy admin, then close the open deadlines and create the first payment item. Everything else is the same on both sides. The only difference is what runs the job.

The same job, two ways

Numbers 1 to 5 are the job machinery. On the left we build and run each piece ourselves. On the right, the same five come from Temporal, which the platform team already runs.

What's identical on both sides: Postgres holds the claim, its status and its deadlines. The status changes in one transaction through the state machine. Outside calls carry idempotency keys. The daily payment run is the same.

Sketches, to compare the shape. On the left, the job has to remember its own step and handle its own failures. On the right, those are settings.

Without Temporal · our job runner
// runs every 2 seconds on every API server
@Scheduled(fixedDelay = 2000)
void runDueJobs() {
  // SKIP LOCKED, and a lease so a crashed
  // runner's jobs are picked up again
  for (Job job : jobs.claimDue(50, Duration.ofMinutes(5))) {
    try {
      switch (job.step()) {
        case 1 -> { letters.sendApproval(job.claimId(), job.key("letter"));
                    jobs.advance(job, 2); }
        case 2 -> { policyAdmin.startWaiver(job.claimId(), job.key("waiver"));
                    jobs.advance(job, 3); }
        case 3 -> { claims.closeDeadlinesAndCreateItems(job.claimId());
                    jobs.complete(job); }
      }
    } catch (Exception e) {
      if (job.attempts() >= 20) { jobs.fail(job, e); alerts.raise(job, e); }
      else jobs.retryLater(job, backoff(job.attempts()), e);
    }
  }
}
// plus: the jobs table and its migrations, backoff(),
// per-call timeouts, the lease logic, the admin screen,
// metrics and alerts, and tests for all of it
With Temporal · a workflow
// Workflow ID: event-E-588, started by the outbox relay
public void run(String claimId) {
  act.sendApprovalLetter(claimId);
  act.startPremiumWaiver(claimId);
  act.closeDeadlinesAndCreateItems(claimId);
}

// retries and timeouts: set once for the activities
ActivityOptions.newBuilder()
  .setStartToCloseTimeout(Duration.ofMinutes(2))
  .setRetryOptions(RetryOptions.newBuilder()
      .setInitialInterval(Duration.ofSeconds(1))
      .setBackoffCoefficient(2.0)
      .setMaximumInterval(Duration.ofMinutes(1))
      .setMaximumAttempts(20)
      .build())
  .build();

// Rules for workflow code: no database calls, no clock,
// no random numbers here. Those go in activities.
// Temporal replays this method to resume it, so it
// must make the same decisions every time.

The same bad day, both ways

What happensWithout TemporalWith Temporal
Policy admin is down for an hourThe runner catches the error, adds 1 to attempts and sets a later try time. Our backoff code decides the wait.The activity's retry settings retry it. The run simply waits at that step.
A server dies just after the approval letter is sentWhen the lease expires, another runner takes the job and resumes at the step saved in the jobs table. If the crash came before "step 2" was saved, the letter is sent again, unless the letters call has an idempotency key.Another worker resumes from the history. A letter step that finished and was recorded isn't repeated. If the worker died during the call, the step runs again, so the letters call still needs an idempotency key.
The same job is started twiceA unique key on the jobs tableThe workflow ID: the second start is refused
A job has been failing for 4 hoursOur alert on attempts or age fires. Someone opens our admin screen.The run fails when its retries run out and Temporal's metrics alert. Someone opens the run in the web UI.
Support asks what happened to C-1042's approvalRead the job row, its last error, and search our logsSearch the web UI by claim ID: every step, with its input, output and error
Change how letters are retriedChange the runner's code and deployChange the activity's retry settings and deploy
Run the deadline dispatcher every minuteSpring's scheduler plus a lock, so only one server runs itA Temporal Schedule. A run that would overlap the previous one is skipped.
Add a step to the job while jobs are mid-flightAdd a case to the switch. Jobs in flight pick up the new numbering, so steps must never be renumbered.Add an activity call. Runs in flight finish on the old code, pinned to their build. New runs get the new code.

The trade, plainly

Without Temporal

  • Nothing new to learn or depend on
  • We build, test and run five pieces of machinery, and keep them working for the life of the platform
  • Every job's code carries its own step tracking and error handling
  • Many teams do this successfully. It's a real option, just more of our own code.

With Temporal

  • The five pieces come ready-made and are already run by the platform team
  • Job code is a plain list of steps
  • We depend on a shared platform, so payments don't use it (failure 17 on the failure page)
  • The team has to learn the workflow rules: no I/O, clock or randomness in workflow code
