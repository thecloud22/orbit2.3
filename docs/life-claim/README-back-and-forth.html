Life claim: things bounce back

This follows one life claim where five things come back instead of going straight through. A worker restarts in the middle of a run. A W-9 fails the IRS check. The death certificate is a photocopy, and the letter asking for a certified copy fails to send. Then, after payment, the bank returns one beneficiary's money. The claim goes back and forth between people, Postgres, Temporal and outside systems. It closes, reopens and closes again.

It's the same claim as the life claim README: Robert Castellano, whole life WL-0804419, $200,000, with Diane and Mark taking 50% each. The mock plays it step by step. Rule values (15 and 30 days, 3.5% interest, the retry settings) are examples.

Temporal never holds the claim while it waits. Each time something comes back, the change is saved in Postgres first. Then a new short workflow does whatever needs an outside system. If that work fails, Temporal retries it; if the retries run out, a person re-runs it. Waiting for a person, a document or a bank is a deadline row, not a sleeping workflow.

Bounce 1 · Fri 25 Sep

A worker restarts in the middle of the intake run

The notice is saved with its outbox event, and the relay starts orch-L-26-043310-intake. Steps 1 to 8 run on worker A. During step 9, sending the acknowledgement and claim packets, a deploy restarts worker A before it reports back.

What Temporal did

When the activity timed out, Temporal scheduled step 9 again, and worker B picked it up. To continue after step 9, worker B replayed the workflow's history, so steps 1 to 8 used their recorded results and didn't run again. The run took 1 min 14 s instead of 41 s.

Why no letter went twice

Each send carries an idempotency key, such as intake:<claim>:ack. The letters service had already sent under that key, so the retry was a no-op. Temporal guarantees the retry; the key makes it safe. The Java slice already does this in IntakeSetupService.sendAcknowledgementAndPackets.

Bounce 2 · 29 Sep to 2 Oct

Diane's W-9 fails the IRS check

Diane e-signs her claimant statement and W-9 in the portal. The event workflow checks her name and taxpayer number with the IRS and gets back "no match". She had transposed two digits. The corrected W-9 arrives three days later.

What Temporal did

Nothing special, and that's the point. "No match" is an answer, not an error, so the activity returned normally and the workflow took its not-enough branch. Temporal retries only when an activity fails, for example on a timeout or a 503.

What Postgres kept

The requirement stayed open, marked "Not enough · TIN mismatch". Its follow-up row D-706 closed, and D-708 was written to chase the correction in 7 days. The corrected W-9 is a new event and a new workflow, event-E-9005. It reads the requirement from Postgres and knows nothing about the first try.

Bounce 3 · Thu 1 Oct

A photocopied certificate, and a letter that won't send

The mail room scans a death certificate with no raised seal. The rules can't accept it, so the workflow hands it to Rachel and ends. At 15:20 Rachel rejects it. Her decision is saved, but the letter asking Diane for a certified copy fails: the letters service is down. At 16:05, Claims ops re-runs the workflow. The certified copy arrives on 9 Oct.

What Temporal did

It retried the send five times, waiting 2, 4, 8 and 16 seconds between attempts, then stopped as the retry policy says. The run shows as failed in Temporal's UI, and its last step opened an ops task. Workflows start with the ID-reuse policy ALLOW_DUPLICATE_FAILED_ONLY, the setting in TemporalWorkflowLauncher. A completed ID can't start again, which is what makes a duplicate outbox start a no-op. A failed one can, which is why ops could start run 2 of event-E-9004: there's still one workflow per event. Under Temporal's default policy, a completed ID could start again.

What wasn't lost

Rachel's decision was saved in Postgres before the workflow started: requirement requested again, D-705 and D-709 closed, D-710 written. Only the letter waited, and it carried the same idempotency key on run 2, so Diane got one letter. Waiting for Rachel was a work item plus the review row D-709. It wasn't a workflow sleeping for four hours.

Bounce 4 · 5 to 7 Oct

Mark is late, so a deadline fires

This is the usual path when something is late, and it's here for comparison. Mark's statement isn't in by day 10, so his follow-up row comes due.

What Temporal did

A Temporal Schedule runs the dispatcher every minute. The dispatcher claims due rows with FOR UPDATE SKIP LOCKED and starts one workflow per row, with the row's ID as the workflow ID. deadline-D-707 re-checks that the statement is still missing before it sends anything.

What Postgres kept

D-707 is marked done, and D-711 is written for 15 Oct. When Mark signs on 7 Oct, the same transaction that accepts his statement closes D-711, so it never fires. Of the 16 rows on this claim, D-707 is the only one that fires.

Bounce 5 · 13 to 20 Oct

The bank returns Mark's payment, so the claim reopens

The daily payment run pays both beneficiaries on 13 Oct, and the claim closes. On 15 Oct the bank's return file shows Mark's EFT came back: the account is closed (R02). The claim reopens and waits for his new account. The replacement is paid on 20 Oct, and the claim closes again.

Batch and Temporal, back and forth

Batch never changes the claim itself. The returns job marks the payment item returned and writes an event. event-E-9010 does the claim side: it reopens the claim, stops payments to the closed account, and asks Mark and tells Rachel. Mark's new account is another event. The replacement goes back to batch in the next payment run, and its confirmation closes the claim again.

What Postgres kept

The returned item stays as it was, because paid items are never edited. The replacement is a new item for the same amount: interest stopped at the first payment, because the return came from the closed account (an example rule). D-715 waited four days for the new details and closed without firing, and D-716 held the 2-business-day reissue target.

What never happened

  • No workflow slept waiting.Waiting for Rachel, for Diane's correction, for the certified copy and for Mark's bank details were all deadline rows and work items in Postgres.
  • No signal went to a long-running workflow.There isn't one. Each thing that happened started its own short workflow.
  • Batch never changed the claim.The payment run and the returns job changed payment items and wrote events; workflows did the claim side.
  • No paid item was edited.The returned item keeps its history, and the replacement is a new item.
  • No letter went twice.Every send carries an idempotency key, so the retry after the restart and run 2 of the letter workflow were both safe.
  • Nothing was lost in the outage.Rachel's decision was committed before the letter's workflow started. Only the letter waited.

Play it in the mock

  1. Run ./claims.sh web, or cd web && npm run dev, and open http://localhost:5173/#/intake/life.
  2. Caller: tick both identity checks and answer the agent question.
  3. The deceased: under How the mock plays this claim, choose Things bounce back.
  4. Policies: tick the read-back. Beneficiaries: press Fill sample answers and answer "anyone else" with No. Review: tick the read-back and submit.
  5. On Workflow & SLA, press Play next 14 times. The Workflow runs tab shows each run with a "What Temporal did" note, including the failed run and its run 2. The claim's Documents, Payments and History sections change as you go.

To check it end to end: node scripts/life-flow-check.mjs <dir> bounce from web/ runs the path in headless Chrome, saves screenshots and asserts 29 outcomes. The code is in web/src/api/lifeFlow.ts: bounceScript and the handlers under "Variation: things bounce back".

The mock plays this whole scenario. The Java slice in backend/ has the intake orchestration, with this retry policy (5 attempts, waits doubling from 2 s) and the idempotent letters from bounce 1; the ID-reuse policy from bounce 3; and the requirement follow-up and dispatcher from bounce 4. TIN matching, document review, the letter workflow and payment returns are still design only.
