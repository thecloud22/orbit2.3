Temporal, Layer by Layer

The same claim as How Temporal Runs a Claim: Sam Ortiz, approved on day 42. Here it's taken apart one layer at a time, to answer three questions. What starts Temporal? What is the dispatcher? Who fires the 30-day and 60-day letters?

Three short answers

  • What starts Temporal?Our code, almost always. Two small pieces of our code call Temporal's "start workflow": the outbox relay, when someone does something, and the dispatcher, when a deadline comes due. Temporal starts only one thing on its own: the dispatcher, once a minute, through a Schedule we set up once.
  • What is the dispatcher?A tiny workflow of ours that runs every minute, for all claims at once. It asks Postgres "which deadlines are due now?" and starts one short workflow for each. It's the only thing that turns a date into action.
  • Does Temporal fire the 30-day and 60-day letters?Not directly. The 30-day letter is a row in the deadlines table, due on day 30. On day 30 the dispatcher's query finds it and starts the letter workflow, and that workflow writes the day-60 row. Temporal holds no 30-day timer.

The layers, and the only two ways in

Six layers, top to bottom. Path A on the left is how every event starts a workflow. Path B on the right is how every deadline does. Every run in Sam's claim takes one of these two paths: runs 1, 2, 3, 4, 6 and 7 take path A, and run 5 takes path B.

Path A · Sam uploads forms

  1. 114:10:00Sam uploads the claim forms. The portal calls the Claims API: POST /claims/C-1042/documents.
  2. 214:10:00The API saves two rows in one Postgres transaction: the document, and outbox row E-501 saying "a document arrived for C-1042". Then it answers Sam's browser. Temporal hasn't been touched yet. If the API crashed now, the outbox row would still be there.
  3. 314:10:01The outbox relay, a small loop inside the Claims API, asks Postgres for new outbox rows every second. It finds E-501.
  4. 414:10:01The relay asks Temporal to start a DocumentReceived workflow named event-E-501, then marks E-501 started. If it crashes before marking, it tries again later, and Temporal rejects the second start because the name is taken.
  5. 514:10:01Temporal records the start and puts a task on the "claims" queue. A claims worker, which is always asking that queue for work, picks it up and runs the workflow code.
  6. 614:10:16The workflow's activities write to Postgres: match the document to its requirement, close the forms follow-up deadline, create an examiner task. The run ends.

Path B · the 30-day status letter

  1. 109:00:00Temporal's Schedule starts a new dispatcher run, as it has every minute since we set it up. This is the only thing Temporal starts on its own, and it isn't about Sam's claim: it's for all claims.
  2. 209:00:00The dispatcher asks Postgres for deadline rows that are open and due by now, and marks them dispatched in the same statement. One of them is D-311, written on day 0 when intake set up Sam's claim.
  3. 309:00:01For each due row, the dispatcher asks Temporal to start a workflow named after it: deadline-D-311. The dispatcher run then ends.
  4. 409:00:01Temporal records the start, and a claims worker picks up the task, exactly as in path A.
  5. 509:00:02The StatusLetter workflow checks the claim first. Still undecided, so the letter is due. It sends the letter through the letters vendor.
  6. 609:00:03In one transaction it marks D-311 done and writes D-312, the next status letter, due on day 60. At 09:01 the dispatcher runs again and finds nothing for Sam: D-311 is done, and D-312 isn't due for 30 days.

The dispatcher, minute by minute

The dispatcher never waits for a date. It just asks, every minute, "what's due now?" Most minutes the answer is nothing.

So who stops the day-60 letter? The approval workflow on day 42 cancels D-312. On day 60 the dispatcher's query doesn't see it, so nothing happens. If that cancel had somehow been missed, the StatusLetter workflow would still check the claim first, find it decided, skip the letter and record why. There are two separate guards.

The code, in four pieces

Sketches in Java, to show the shape. Check the exact method names against the Temporal SDK version the platform team runs.

1 · The Schedule · set up once, at deploy
// Temporal fires this every minute, by itself.
scheduleClient.createSchedule(
  "deadline-dispatcher",
  Schedule.newBuilder()
    .setAction(ScheduleActionStartWorkflow.newBuilder()
      .setWorkflowType(DispatcherWorkflow.class)
      .setOptions(WorkflowOptions.newBuilder()
        .setWorkflowId("deadline-dispatcher")
        .setTaskQueue("claims").build())
      .build())
    .setSpec(ScheduleSpec.newBuilder()
      .setIntervals(List.of(
        new ScheduleIntervalSpec(Duration.ofMinutes(1))))
      .build())
    .build(),
  ScheduleOptions.newBuilder().build());
2 · The dispatcher · a workflow, run every minute
public void run() {
  // activity: the SQL below
  List<Due> due = act.claimDueDeadlines(500);
  for (Due d : due) {
    // activity: start "deadline-" + d.id()
    // a name that's taken counts as done
    act.startDeadlineWorkflow(d);
  }
}

-- claimDueDeadlines
UPDATE deadline
   SET status = 'dispatched', dispatched_at = now()
 WHERE id IN (
   SELECT id FROM deadline
    WHERE status = 'open' AND due_at <= now()
    ORDER BY due_at LIMIT 500
    FOR UPDATE SKIP LOCKED)
RETURNING id, kind, claim_id;
3 · One deadline's workflow · status letter
// Workflow ID: deadline-D-311
public void run(String deadlineId) {
  Deadline d = act.load(deadlineId);
  if (!act.claimStillUndecided(d.claimId())) {
    act.skip(deadlineId, "claim decided");
    return;
  }
  act.sendStatusLetter(d.claimId());
  // one transaction: D-311 done,
  // next status letter written for +30 days
  act.finish(deadlineId, Duration.ofDays(30));
}
4 · The outbox relay · in the Claims API
// Spring runs this every second.
@Scheduled(fixedDelay = 1000)
void relay() {
  for (OutboxRow row : outbox.claimNew(100)) {
    try {
      client.newUntypedWorkflowStub(row.workflowType(),
          WorkflowOptions.newBuilder()
            .setWorkflowId("event-" + row.id())
            .setTaskQueue("claims").build())
        .start(row.payload());
    } catch (WorkflowExecutionAlreadyStarted e) {
      // started before we could mark it: fine
    }
    outbox.markStarted(row.id());
  }
}

Why not let Temporal wait 30 days itself?

It could. Temporal has durable timers, and this would be a valid design. We chose not to, and here's the difference.

Not chosen · one workflow per claim, alive for months
// inside a workflow that lives until the claim closes
Workflow.sleep(Duration.ofDays(30)); // Temporal's timer
act.sendStatusLetter(claimId);
  • Temporal would fire the letter itself on day 30.
  • The deadline would be invisible to SQL. Examiners and compliance couldn't list it, report on it or extend it without sending a message to the workflow.
  • Changing 30 days to 45 for claims already running would mean changing code under workflows that have been waiting for weeks.
Chosen · a row, plus a dispatcher every minute
INSERT INTO deadline (id, claim_id, kind, due_at, status)
VALUES ('D-311', 'C-1042', 'status_letter',
        '2026-10-26 09:00', 'open');
  • Anyone can see, report on and extend the deadline. An extension is an UPDATE with a reason.
  • Each firing runs today's code, and runs are short, so changes are safe.
  • The costs: one query a minute, letters up to a minute after their due time, and every state change has to remember to write its rows. That's failure 1, with a nightly check behind it.

So what does Temporal give us, if our code does the starting?

Our code decides when work starts. Temporal makes sure that work, once started, finishes: in order, exactly once, through crashes and outages, with a record of every step.

What we needWithout Temporal, we build itWith Temporal
Finish a multi-step job even if a server dies halfwayA jobs table with a "last step done" column, and code in every job to resume from that stepThe event history. Our code stays a plain list of steps.
Retry a failing outside call, with growing waits and a give-up timeA retry scheduler, attempt counters and backoff logicA setting on each activity
Never run the same job twiceLocks and unique keys in every job runnerWorkflow IDs: a second start is refused
Stop waiting for a call that hangsTimeouts wrapped around every callA timeout setting on each activity
Find a failed job, see why, and re-run itOur own admin screen, logs and re-run toolingThe Temporal web UI: search by claim ID, see each step's input, output and error, retry or reset
A recurring job that never overlaps itselfA cron job plus a lockA Schedule, with an overlap rule, pause and resume
Run all of that in productionOur team operates itThe platform team already does

7 · decisionletters vendor, policy adminA lot. The approval letter and the premium waiver must both happen, even if policy admin is down for an hour.

4, 6 · proof complete, review donenone: Postgres onlyLittle. This work could run inside the API's own transaction, with no workflow at all.

A rule of thumb for the team: use a workflow when a job calls something outside Postgres, or has several steps that must all happen. If the job only writes Postgres, do it in the same transaction as the event that caused it. Applied to Sam's claim, runs 4 and 6 would stop being workflows, leaving five runs, and each of those five does something Temporal is good at.
