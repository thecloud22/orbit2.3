Claims platform · disability continuation

Continuation Break Points

The proposed split: Temporal runs a claim from intake to approval, one continuation workflow per disability claim clears each month's payment, and a daily batch run pays what's cleared. The red numbers mark every place this can break.

Where it can break

What breaks at each point

#WhereWhat breaksGuard
1Opening a periodA wrong schedule end date means no item, so the claimant is silently unpaid. Or a retry opens the period twice and sends two proof letters.Unique key on benefit line + period. Nightly check: one item for every period that's due.
2Continuation workflowThe workflow fails or is terminated, and nothing starts the next cycle.Nightly check: every claim in continuation has a running workflow. Alert on any failed workflow.
3Requests and remindersWorkers are down for two days, then every timer fires at once and sends reminders for proof that already arrived. Or a suspension goes through but its letter fails.Timers use absolute dates. The workflow re-reads Postgres before any letter. The letter goes out before the status changes.
4Proof arrivingProof is late, early, covers several months or several policies, or arrives on paper a week later. A signal to a finished workflow fails and the document sits unattached.Attach to the claim in Postgres first, recording which periods and benefit lines it covers, then signal. No running workflow means an examiner task.
5CalculatingThe wrong rules version is used. The claimant switches between residual and total disability. Tax-return true-ups, partial months and appeals change periods already paid.Rules version pinned on the benefit line and stored with each calculation. Paid items are never edited; corrections are new adjustment items.
6Clearing or holdingThe workflow and an examiner change the same item at the same moment. Whichever write lands last wins.One state machine for item status, which checks the current status before any change. Human decisions win over automatic ones.
7ExaminerA forgotten hold means silent non-payment. A review task for every proof creates a backlog, and payments go out late.Every hold has an owner and a review date. Clear automatically when proof is unchanged.
8Claim closingRecovery, death or the end of the benefit period arrives while items are open or already in a bank file, causing an overpayment.Closing cancels open items in the same transaction. The payment run re-checks claim status. A stop after the file has gone becomes a recovery task.
9Payment run and bankTwo runs take the same item. The file is sent twice or not at all. The run doesn't happen.Items taken in one step, stamped with the run ID. File IDs and bank acknowledgement. An alert from outside the batch if the run is late.
10ReturnsA payment is returned, and next month pays the same closed account.The hold goes on the payee's payment method, not the item.
11Go-live conversionIn-flight claims are loaded with the wrong item statuses, or without a running workflow.Rehearse the conversion. Run the nightly checks on converted data before cutover.

The payment item: who can change it

Checked every night

These checks don't prevent a break. They make sure one shows up within a day instead of in a complaint to the Department of Insurance.

  • Every active benefit line has exactly one item for each period that's due.catches 1211
  • Every claim in continuation has a running continuation workflow.catches 211
  • No document is left unmatched to a period, and no proof sits unreviewed past its limit.catches 47
  • No item is paid for a period after the claim's end date or date of death.catches 8
  • Every suspension has a letter; every hold has an owner and a review date that hasn't passed.catches 37
  • No item stays cleared for more than a set number of days without being paid, and paid items match bank confirmations to the cent.catches 9
