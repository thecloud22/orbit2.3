How Temporal Runs a Claim

One clean disability claim, followed from Temporal's point of view. Sam Ortiz, a dentist, injures a hand and can't work. Sam files a claim, the evidence comes in on time, a medical consultant reviews it, and the examiner approves on day 42.

Temporal doesn't hold Sam's claim for 42 days. It runs seven short jobs, about a minute of work in total. Between them, the claim is just data in Postgres.

For what starts each run, what the dispatcher is and who fires the 30-day and 60-day letters, see Temporal, Layer by Layer.

Seven words to know

The pattern in every row: the status change and everything that must happen with it are saved together in one transaction. Anything that calls outside Postgres, like letters or policy admin, is done afterwards by a Temporal run, with retries.

Inside one run: the intake checks

Run 1, on day 0. On the left, the code we write. On the right, what Temporal writes down as it runs. The history is simplified: Temporal records a few more bookkeeping events.

Our workflow code (Java)
// Workflow ID: orch-N-5531-intake
public void run(String noticeId) {
  Policy policy = act.findPolicy(noticeId);
      // calls policy admin
  act.screenSanctions(policy.insured());
      // calls the sanctions list
  act.checkForDuplicate(policy.insured(), noticeId);
      // reads Postgres
  String claimId = act.createClaim(noticeId, policy);
      // one Postgres transaction: claim, benefit
      // line, 3 requirements, first deadlines
  act.sendLetters(claimId);
      // acknowledgement and claim forms
}
// Blue lines are activities. Temporal records
// each one and retries it if it fails. If a check
// finds a problem, the real code opens a task
// for a person and stops.

Why the history matters: three things that go wrong

3 · The relay tries to start intake twice, because it crashed just after starting it the first time. Temporal refuses the second start: a run named orch-N-5531-intake already exists. Sam gets one acknowledgement letter, not two.

Run 5: a deadline comes due

Day 30, 09:00. The claim is still in review, so the status letter the state requires has to go out.

Run 7: the examiner approves

Day 42, 15:20. A person's action becomes an event, and the event starts a workflow.

Seven runs, about 75 seconds of work across 42 days. Every run is tagged with the claim ID, so the Temporal web UI can list all seven for C-1042 and show each one's history.

What Temporal does in this design, and what it doesn't

Does

  • Runs each multi-step job to the end, even if a server dies part-way
  • Retries failing calls with backoff, using settings rather than code
  • Refuses a second run with the same workflow ID
  • Keeps a searchable history of every run, for support and audit
  • Runs the deadline dispatcher every minute

Doesn't

  • Hold the claim. Postgres does.
  • Hold deadlines. The deadlines table does, so examiners and compliance can see them.
  • Wait for people. Tasks live in Postgres, and a finished task starts a new run.
  • Move money. The daily payment run does.

Temporal could hold one workflow per claim for all 42 days, waiting on timers and messages. We chose short runs for two reasons: deadlines have to be visible and editable in Postgres, and code for long-running workflows is hard to change safely. The architecture page has the full reasoning.
